# OM WS/UI Integration — Design

**Date:** 2026-07-02
**Status:** Approved (Approach 1: Full Mastra parity)
**Depends on:** `2026-07-01-om-background-detached-buffering.md` (detached buffering shipped)

## Goal

Surface Observational Memory lifecycle to the UI: inline badges in the chat list, token-budget progress bars in a left sidebar, and an expandable observation detail renderer. Badges survive reloads.

## Architecture: Approach 1 (Full Mastra parity)

OM events flow through the existing WS event channel as new `AgentHarnessEvent` variants. Markers persist as `CustomMessage` entries in the session tree (no DB schema migration). The client reduces events into `om_marker` UI parts and reconstructs them on reload.

---

## 1. Event Model

### 5 new `AgentHarnessEvent` variants

Added to `AgentEvent` in `packages/agent/src/types.ts`:

```ts
| { type: "om_start"; cycleId: string; operationType: "observation" | "reflection" | "buffering"; tokenCount: number }
| {
    type: "om_end"; cycleId: string; operationType: "observation" | "reflection" | "buffering";
    durationMs: number; tokensProcessed: number; tokensProduced: number;
    observations?: string; currentTask?: string; suggestedResponse?: string;
  }
| { type: "om_failed"; cycleId: string; operationType: "observation" | "reflection" | "buffering"; error: string; durationMs: number }
| {
    type: "om_activation"; cycleId: string; operationType: "observation" | "reflection";
    chunksActivated: number; tokensActivated: number; observationTokens: number;
  }
| {
    type: "om_status";
    windows: {
      messages: { tokens: number; threshold: number };
      observations: { tokens: number; threshold: number };
    };
    recordId: string;
  }
```

**Design rationale:** Mastra has 12 event types (`om_observation_start`, `om_reflection_start`, `om_buffering_start`, ...). We collapse to 5 using an `operationType` discriminator (`"observation" | "reflection" | "buffering"`). This is leaner while covering the same lifecycle surface.

**`cycleId`:** Generated by the engine (UUID). Shared across `om_start`/`om_end`/`om_failed`/`om_activation` for the same operation. The client matches by `cycleId` to update a single badge in place (not stack duplicates).

## 2. Engine Callback

### `onOmEvent` on `ObservationalMemoryEngineOptions`

**File:** `packages/agent/src/observational-memory/engine.ts`

```ts
export interface ObservationalMemoryEngineOptions {
  readonly deps: ObservationalMemoryDeps;
  readonly abortSignal?: AbortSignal;
  /** OM lifecycle callback — forwarded to the WS bridge by agent-run.ts. */
  readonly onOmEvent?: (event: OmHarnessEvent) => void;
}
```

The engine fires `onOmEvent` at each lifecycle point:

| Event           | Fired from                                                                            | When                                                                        |
| --------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `om_start`      | `runSyncObserve`, `runSyncReflect`, `maybeBufferObservation`, `maybeBufferReflection` | Before the LLM call                                                         |
| `om_end`        | same                                                                                  | After successful completion (with observation text, token counts, duration) |
| `om_failed`     | same                                                                                  | On error (with error message)                                               |
| `om_activation` | `activateBufferedObservations` / `activateBufferedReflection`                         | When buffered content moves to active context (instant, no LLM)             |
| `om_status`     | `maybeObserve`, `maybeReflect` (end of each call)                                     | Reports current window state for progress bars                              |

**Safety:** `onOmEvent` is optional and guarded (`this.onOmEvent?.(...)`). Engine never throws from the callback — it's fire-and-forget. If the callback throws, the error is caught and logged, never propagated.

**`cycleId` generation:** `crypto.randomUUID()` at the start of each observation/reflection cycle. Passed through the internal call chain.

## 3. Persistence — `CustomMessage` entries

### No DB schema migration needed

OM markers persist as `CustomMessage` entries in the existing `session_entries` table:

```ts
// CustomMessage with customType: "om_marker"
{
  role: "custom",
  customType: "om_marker",
  content: "",               // no displayable text content
  display: false,            // excluded from LLM context
  timestamp: Date.now(),
  details: {
    cycleId: "abc-123",
    operationType: "observation",
    status: "complete",      // "loading" | "complete" | "failed" | "buffering" | "buffering-complete" | "buffering-failed" | "activated"
    durationMs: 3500,
    tokensProcessed: 32500,
    tokensProduced: 4100,
    observations: "<observations>...</observations>",
    currentTask: "...",
    suggestedResponse: "...",
  } satisfies OmMarkerDetails,
}
```

**Why `CustomMessage`:**

- `AgentMessage` is already a union including `CustomMessage` — no type change.
- `CustomMessage.details?: T` carries arbitrary structured data — perfect for marker payloads.
- `CustomMessage.display: false` keeps markers out of LLM context (they're UI-only metadata).
- `session_entries` table already stores all entry types — no migration.
- Tree-structured: marker entries appended after the assistant message preserve ordering.

**When markers are persisted:** `agent-run.ts` collects OM events during the run. On turn end (or on `om_end`/`om_failed`), it appends a `CustomMessage({ customType: "om_marker", details })` to the session tree via `session.appendCustomMessageEntry("om_marker", "", false, details)`.

**Multiple markers per turn:** If both an observation and a reflection complete in the same turn, two separate `CustomMessage` entries are appended (one per cycleId).

---

## 4. WS Protocol — Zero server changes

OM events are new `AgentHarnessEvent` variants. They flow through the existing `{ type: "event", event, sessionId }` frame unchanged. The server's `runAgentStream` already forwards all harness events via `emit` — no new frame types, no new routes.

The only wiring change is in `agent-run.ts`: pass `onOmEvent: (e) => emit(e)` to the engine constructor.

## 5. Client Reducer

### New `om_marker` part type

**File:** `apps/desktop/src/stores/types.ts`

```ts
export type MessagePart = { isStreaming?: boolean } & (
  | { type: "text"; text: string }
  | {
      type: "tool_call";
      toolCallId: string;
      toolName: string;
      input: unknown;
      status: "running" | "done" | "error";
      result?: string;
      details?: unknown;
    }
  | { type: "thinking"; text: string; startedAt?: number; endedAt?: number }
  | {
      type: "om_marker";
      cycleId: string;
      operationType: "observation" | "reflection" | "buffering";
      status:
        | "loading"
        | "complete"
        | "failed"
        | "buffering"
        | "buffering-complete"
        | "buffering-failed"
        | "activated";
      durationMs?: number;
      tokensProcessed?: number;
      tokensProduced?: number;
      observations?: string;
      currentTask?: string;
      suggestedResponse?: string;
      error?: string;
    }
);
```

### Event reducer changes

**File:** `apps/desktop/src/stores/session/event-reducer.ts`

New cases in `dispatchEvent`:

| Event           | Action                                                                                                                                                                        |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `om_start`      | `addOmMarker(msgId, cycleId, operationType, status: operationType === "buffering" ? "buffering" : "loading")` — appends `om_marker` part to current or last assistant message |
| `om_end`        | `updateOmMarker(msgId, cycleId, { status: "complete", durationMs, tokensProcessed, tokensProduced, observations, ... })`                                                      |
| `om_failed`     | `updateOmMarker(msgId, cycleId, { status: "failed", error })`                                                                                                                 |
| `om_activation` | `updateOmMarker(msgId, cycleId, { status: "activated" })`                                                                                                                     |
| `om_status`     | `updateOmStatus(windows)` — updates a new `omStatus` field on `SessionStoreData`                                                                                              |

**Message targeting:** The reducer uses `streaming.currentMessageId` if set, otherwise falls back to the last assistant message in `messageOrder`. This handles both sync observations (during a message) and turn-boundary observations (after `message_end`).

### New session store state

**File:** `apps/desktop/src/stores/session/session-store.ts`

```ts
export interface SessionStoreData {
  // ... existing fields ...
  omStatus: OmWindowState | null; // for progress bars
}

export interface OmWindowState {
  messages: { tokens: number; threshold: number };
  observations: { tokens: number; threshold: number };
}
```

## 6. Reload / Hydration

### `hydrateSessionMessages` extended

**File:** `apps/desktop/src/stores/session/hydrate-messages.ts`

When iterating `AgentMessage[]`, `role: "custom"` messages with `customType: "om_marker"` are NOT converted to standalone `UIMessage`s. Instead, their `details` are extracted and appended as an `om_marker` part on the **preceding assistant** `UIMessage`.

```ts
// Pseudocode
if (msg.role === "custom" && msg.customType === "om_marker") {
  const lastAssistant = findLastAssistant(result);
  if (lastAssistant) {
    lastAssistant.parts.push({ type: "om_marker", ...msg.details });
  }
  continue; // don't create a new UIMessage
}
```

**Disconnection handling:** If a reload finds an `om_marker` with `status: "loading"` or `"buffering"` (operation started but never completed — e.g. crash during observation), it's stamped `status: "disconnected"`. This matches Mastra's `markOmMarkersAsDisconnected` pattern.

## 7. UI Components

### 7a. Inline badge — `OmMarkerPart`

**File:** `apps/desktop/src/components/chat-area/parts/om-marker-part.tsx`

Registered in the part registry as `registerPartComponent("om_marker", OmMarkerPart)`.

**Visual states** (Tailwind classes, matching sakti's design tokens):

| Status               | Color                                                 | Content                                               |
| -------------------- | ----------------------------------------------------- | ----------------------------------------------------- |
| `loading`            | `bg-info/10 text-info`                                | Spinner + "Observing ~12.3k tokens..."                |
| `complete`           | `bg-success/10 text-success`                          | Eye icon + "Observed 32.5k→4.1k tokens (-8x)"         |
| `failed`             | `bg-destructive/10 text-destructive`                  | X icon + "Observation failed" (expandable error)      |
| `buffering`          | `bg-accent/10 text-accent-foreground`                 | Spinner + "Buffering observations ~12k tokens..."     |
| `buffering-complete` | `bg-accent/10 text-accent-foreground` (dashed border) | Eye icon + "Buffered 32.5k→4.1k tokens (-8x)"         |
| `buffering-failed`   | `bg-destructive/10 text-destructive` (dashed border)  | X icon + "Buffered observation failed"                |
| `activated`          | `bg-success/10 text-success`                          | Eye icon + "Activated: Observed 32.5k→4.1k tokens"    |
| `disconnected`       | `bg-warning/10 text-warning`                          | Unplug icon + "Observation interrupted (~12k tokens)" |

**Expand/collapse:** Click toggles a detail panel showing:

- Observation text (rendered via `ObservationRenderer`)
- Current task (if present)
- Suggested response (if present)
- Stats row: Input / Output / Compression / Duration

**Token formatting:** `formatTokens(n)` — `<1000` → plain, `>=1000` → `"12.3k"`, `>=1M` → `"1.2M"`.

### 7b. Observation renderer — `ObservationRenderer`

**File:** `apps/desktop/src/components/chat-area/parts/observation-renderer.tsx`

Parses observation text with priority emoji into colored cards:

- `🔴 P1` → `border-l-destructive bg-destructive/5`
- `🟡 P2` → `border-l-warning bg-warning/5`
- `🟢 P3` → `border-l-success bg-success/5`

Renders inside the expanded badge.

### 7c. Progress bars — `OmProgressBars`

**File:** `apps/desktop/src/components/layout/sidebar/om-progress-bars.tsx`

Two side-by-side mini progress bars in the left sidebar:

- **Messages:** `pendingMessageTokens / messageTokensThreshold`
- **Observations:** `observationTokenCount / observationTokensThreshold`

**Bar fill color by percentage:**

- `< 60%` → `bg-success` (green)
- `>= 60%` → `bg-info` (blue)

**Processing state** (when active AND >= 100%): bar shows live timer "observing 12.3s" or "reflecting 8.1s" instead of percentage.

**Collapsed state:** Thin 1px bar at the bottom of the sidebar card.

### 7d. Memory sidebar card — `MemorySidebarCard`

**File:** `apps/desktop/src/components/layout/sidebar/memory-sidebar-card.tsx`

Collapsible card in the left sidebar containing:

- Config pills (observational memory enabled/disabled indicator)
- The two progress bars (when expanded)
- Thin 1px progress bar (when collapsed)

Reads from `session.store.omStatus` (populated by `om_status` events).

## 8. Data Flow Summary

```
OM Engine (packages/agent)
  │ onOmEvent({ type: "om_start", cycleId, ... })
  │
  ▼
agent-run.ts
  │ emit(event)  →  WS bridge
  │
  │ On om_end/om_failed:
  │ session.appendCustomMessageEntry("om_marker", "", false, details)
  │                                       ↓
  │                            session_entries table (persisted)
  │
  ▼
WS frame: { type: "event", event: { type: "om_start", ... }, sessionId }
  │
  ▼
ws-client.ts handleFrame → dispatchEvent
  │
  ├─ om_start  → addOmMarker (new om_marker part, status: loading)
  ├─ om_end    → updateOmMarker (status: complete, observations, tokens)
  ├─ om_failed → updateOmMarker (status: failed, error)
  ├─ om_activation → updateOmMarker (status: activated)
  └─ om_status → updateOmStatus (progress bars)
  │
  ▼
UI Components
  ├─ OmMarkerPart (inline badge, 8 states, expand/collapse)
  ├─ ObservationRenderer (priority emoji → colored cards)
  ├─ OmProgressBars (two bars in sidebar)
  └─ MemorySidebarCard (collapsible card)
  │
  ▼
On reload:
  GET /messages → AgentMessage[] including CustomMessage(om_marker)
  │
  ▼
  hydrateSessionMessages → om_marker parts on assistant UIMessages
```

## 9. Implementation Phases

### Phase 1: Event plumbing (agent + server)

1. Add 5 `om_*` event types to `AgentEvent` union
2. Add `onOmEvent` callback to engine options
3. Engine fires events at lifecycle points (start/end/failed/activation/status)
4. `agent-run.ts` wires `onOmEvent` to `emit`
5. Persist markers as `CustomMessage` entries on turn end

### Phase 2: Client state (desktop store)

6. Add `om_marker` to `MessagePart` union
7. Add `omStatus` to `SessionStoreData`
8. New session store actions: `addOmMarker`, `updateOmMarker`, `updateOmStatus`
9. Extend `dispatchEvent` reducer with 5 new event cases
10. Extend `hydrateSessionMessages` to reconstruct `om_marker` parts from `CustomMessage`

### Phase 3: UI components (desktop renderer)

11. `OmMarkerPart` component (inline badge, 8 states, expand/collapse)
12. `ObservationRenderer` component (priority emoji parsing)
13. Register `om_marker` in part registry
14. `OmProgressBars` component (two bars)
15. `MemorySidebarCard` component (collapsible sidebar card)
16. Wire sidebar into the desktop layout

---

## 10. Testing Strategy

- **Engine unit tests:** verify `onOmEvent` fires with correct payloads at each lifecycle point
- **Event reducer tests:** verify `om_start`/`om_end`/`om_failed`/`om_activation` create/update markers correctly
- **Hydration tests:** verify `CustomMessage(om_marker)` → `om_marker` part reconstruction
- **Component tests:** verify badge renders all 8 states, progress bars render correct percentages/colors
- **Integration:** verify events flow from engine → WS → reducer → UI in a full agent run
